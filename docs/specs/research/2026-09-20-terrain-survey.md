## The "Write a Note" feature as built (Flutter app at /Users/satanshumishra/Documents/DevLabs/fireplace)

**BLUF.** The composer is a raw `EditableText` (not `TextField`) driven by a plain `TextEditingController`, living in a fixed-height 440px sheet inside a `showGeneralDialog` route. Note text is a single nullable `text_content TEXT` column; the write path is composer -> CaptureService -> JournalRepository -> EntriesDao -> drift, and the edit path deliberately bypasses CaptureService entirely and calls `updateEntryText` directly, so create and edit are asymmetric. Responsiveness in this app is not width-based at all — every layout branch keys on `TargetPlatform`, and there is not a single `MediaQuery` width read in `lib/`.

### Options this area leaves open

- Keep `entries.text_content` as the single note column and store markdown source in it. This is the only change that requires NO schema migration, which matters because `onUpgrade` currently throws (lib/data/database/app_database.dart:25-32).
- Encode photo placement inside the markdown source itself (an image node with attributes) rather than in new DB columns — again avoiding the migration cliff, at the cost of making the search haystack and export JSON contain syntax.
- Alternatively extend `entry_photos` with placement columns (anchor offset, side, width fraction, intrinsic w/h). This is the cleaner data model but forces authoring a real drift migration AND removing the unconditional `onUpgrade` throw before any release.
- Swapping the renderer is cheap: `NoteBody` has exactly one production call site (entry_card.dart:136), and `EntryCard` has exactly two (today_entry_feed.dart:109, day_detail_entry_tile.dart:29). A rich renderer is a 1-to-3 file blast radius in production code.
- Swapping the composer is also structurally cheap: `TextComposerSheet` has exactly two production consumers (the create connector and the edit connector), so create and edit inherit any editor change for free — but the edit path's direct `updateEntryText` call means validation added to CaptureService will NOT apply to edits unless that asymmetry is also addressed.
- Replace raw `EditableText` with `TextField` (or wrap it in `TextSelectionGestureDetectorBuilder`) to get selection handles, the copy/paste toolbar, and a selection highlight for free — currently all three are absent.
- Introduce genuine width-based breakpoints. Nothing today reads width, so a breakpoint layer would be new infrastructure rather than a modification; conversely nothing existing will fight it.
- Reuse or delete the dead photo layer. `PhotoPicker`/`ImagePickerPhotoPicker` (with its mime mapping and permission-error messages) is genuinely reusable; `PhotoTray` and `PhotoThumbnail` encode a non-positional attachment-strip model and would need replacing, not adapting.
- Wire the already-built but unconsumed `textScaleProvider` into the editor and renderer so the existing text-size setting finally does something — relevant because responsive text sizing is part of the brief.

### Ruled out, with reason

- **Derive image aspect ratio cheaply from the database to lay out text wrap without decoding files** — `media_blobs.width`/`height` are nullable and are never populated for photos: `photoCaptureFromXFile` builds `CaptureFile(file:, mime:)` with no dimensions (lib/features/capture/photo/image_picker_photo_picker.dart:30-36), and `_finalize` merely forwards whatever CaptureMedia carries (lib/features/capture/core/journal_capture_service.dart:150-157). Every existing photo row would have NULL dimensions even if the write path were fixed today.
- **Add columns or tables via a routine drift migration** — `schemaVersion` is 1 and `onUpgrade` throws a StateError unconditionally for every from/to pair (lib/data/database/app_database.dart:17,25-32). A schema change is not a migration-authoring task, it is a migration-infrastructure task that must first remove a deliberate hard-fail.
- **Reuse the existing photo tray as the scrapbook placement surface** — `PhotoTray` models photos as an ordered list capped at 8 with no position data (lib/features/capture/photo/photo_tray.dart:9,34,45), and the persisted `EntryPhoto` carries only `sortOrder` (lib/domain/models/entry_photo.dart:12-18). There is no anchor, coordinate, float side, or size field to reuse.
- **Build on existing responsive/adaptive layout primitives** — None exist. Every branch is `platform == TargetPlatform.macOS` (lib/app/shell/shell_layout.dart:5-9, lib/features/today/today_layout.dart:7-11). There is no breakpoint constant, no width read, and no adaptive helper in lib/. On a large Android tablet the app renders the phone layout; in a narrow macOS window it renders the desktop rail.
- **Assume the composer already handles the Android software keyboard** — It is a `showGeneralDialog` route above the Scaffold, so `resizeToAvoidBottomInset` never reaches it, and no composer widget reads `viewInsets` (only bottom_bar_shell.dart uses SafeArea). Measured at 360x640 with a 320px keyboard, 44.8% of the writing area is occluded.
- **Assume text selection, copy and paste already work in the composer** — With `selectionControls == null && contextMenuBuilder == null`, Flutter disposes the selection overlay (editable_text.dart:4422). Probe confirmed no AdaptiveTextSelectionToolbar, no handles, and `selectionColor == null` so the selection is not even painted.
- **Treat create and edit as one code path that will inherit editor changes uniformly** — They share only the presentational `TextComposerSheet`. Create goes composer -> CaptureService -> repository with a 20s timeout and server-side blank/trim validation; edit goes connector -> repository directly with a confirmation dialog and no timeout (lib/features/day_detail/day_detail_edit_note.dart:49-76). Any validation, normalisation, or media handling added to CaptureService silently does not apply to edits.

## Storage, schema and media (Flutter/Drift app at /Users/satanshumishra/Documents/DevLabs/fireplace)

**BLUF.** Body text is an uncapped, unconstrained `TEXT NULL` column with no format discriminator, so a markdown body needs zero schema change to store. The photo terrain is the real constraint: images are content-addressed SHA-256 blobs on disk, but `media_blobs.width`/`height` are NULL for every photo ever captured, originals are stored un-downscaled, and decode happens at full resolution — so nothing in the data layer can currently tell a layout engine an image's aspect ratio. ### Options this area leaves open

- Migration-free, body-embedded: store layout directives inside `entries.text_content` itself (e.g. markdown image syntax carrying attributes). Zero schema change, exports losslessly today, immune to the hand-written-mapper drop, and nothing needs a version bump. Cost is that layout data becomes part of the text the user can corrupt by editing, and search indexes it.
- Migration-free, KV sidecar: store per-image layout JSON in the existing `settings` table under composite keys. Proven to work with no schema change and it already exports. Needs its own DAO (the settings repository is closed to new keys) and needs explicit cleanup wired into delete-all and media GC, or rows orphan permanently.
- Additive migration: add nullable columns (e.g. a body-format discriminator on `entries`, a layout JSON blob on `entry_photos`). Measured cost is a drift/drift_dev bump to 2.35.0, a 6-line build.yaml, ~4 lines of onUpgrade, and edits to exactly two existing tests; 5,297 lines of snapshot and test scaffolding generate themselves and the data-integrity test passes.
- New table for placements, keyed to entry + media, leaving `entry_photos` as-is for the legacy strip. Same migration machinery cost as above; keeps the sequence-only model intact while giving placements their own identity and soft-delete.
- Backfill-style out-of-band data fix in the BlobExtensionBackfill mould (guarded, idempotent, run at provider init) for anything that needs to touch existing rows without a schema version change — there is working, tested precedent for this pattern in-repo.
- Populate `media_blobs.width`/`height` at capture (the columns already exist and the store already plumbs them) so a layout engine can reserve space and compute aspect ratio without decoding. This needs no schema change at all — only the capture call sites.
- Add decode-time downscaling (`cacheWidth`/`ResizeImage`) and/or store a derived display-size variant as a second content-addressed blob. The blob store's dedup and atomic-write machinery supports extra derived blobs with no schema change.
- Use FTS5 or json1, both confirmed present in the bundled SQLite 3.53.3, if search or queryable layout metadata becomes a requirement.

### Ruled out, with reason

- **Write a drift migration test today using `SchemaVerifier` without touching pubspec** — `import 'package:drift_dev/api/migrations.dart'` fails to compile at the pinned drift_dev 2.34.0 / drift 2.34.2 pair — `_GenerateFromScratchDrift3` is missing `GeneratedDatabase.schema` and `allSchemaEntities` is undefined. The CLI (`dart run drift_dev`) fails identically. A version bump is a hard prerequisite for any use of drift's own migration tooling.
- **Store per-image placement data on `media_blobs`** — Blobs are content-addressed by SHA-256 and deduplicated — `_finalize` returns the existing row when the digest already exists (filesystem_media_store.dart:133-136). The same image placed twice in one note, or used in two different notes, is ONE row. Per-placement data cannot live there without breaking dedup.
- **Read aspect ratio from `media_blobs.width`/`height` to lay out and wrap text** — Those columns are NULL for every photo in existence. The sole photo construction site (image_picker_photo_picker.dart:35) passes neither. Any layout engine relying on them gets null today; the capture sites must be fixed first.
- **Validate a new body format by round-tripping it through export and import** — No importer exists anywhere in the codebase. There is no ZipDecoder, no restore path, and file_picker is used only for saveFile. Export is strictly one-way, so a round-trip cannot be exercised at all.
- **Add a schema column and rely on the existing export to carry it** — The three row-to-JSON mappers in journal_export_service.dart (lines 125-158) are hand-written field lists with no reflection and no test comparing them to the table definitions. A new column is silently omitted from every export with no error — the export would appear to succeed while losing the data.
- **Put layout metadata in `settings` and assume existing cleanup handles it** — The settings table is untouched by delete-all (journal_delete_all_service.dart:24-30 deletes only the four journal tables) and invisible to media GC (media_gc.dart:26-51 walks only entries and entry_photos). Orphan rows would survive a full journal wipe and accumulate forever unless cleanup is written explicitly.
- **Treat the throwing `onUpgrade` as a data-loss risk that must be removed before anything else** — Measured non-destructive: after a failed upgrade attempt `PRAGMA user_version` is still 1 and all rows are intact and readable by the v1 build. It refuses to open, which is loud and recoverable, not lossy. It is a deliberate fail-safe, not a hazard to be defused under time pressure.

### Open questions

- Does the product want photos addable to an ALREADY-SAVED entry? Today that is impossible: `addPhoto` is only reachable from the capture flow and `softDeletePhoto` has no callers. A scrapbook editor almost certainly needs both, and that is feature work independent of any schema decision.
- HEIC decodability on Android is unverified. The MIME map accepts image/heic and image/heif and image_picker returns originals un-transcoded on Android, but I did not confirm whether Flutter's `Image.file` can decode them on the target API levels. If it cannot, affected photos render as the corrupt placeholder.
- What are real-world blob sizes in this app? No downscale happens, so a modern phone photo is stored at full size, but I could not measure actual device data from here.
- Should `exportFormatVersion` bump if the body format changes? Nothing reads it back today (no importer), so the decision is about future-proofing rather than present correctness.
- Should the 8-photo-per-entry cap survive into a free-placement scrapbook model? It is a UI constant with no backing constraint, so it is cheap to change either way.
- Is a real importer in scope? Its absence means the export is currently a one-way archive, and any claim about a body format "surviving a round-trip" is untestable until one exists.
- Does the team want the drift/drift_dev bump to 2.35.0 regardless of the storage decision? The broken CLI and unusable SchemaVerifier are a latent trap that will surface the moment anyone touches the schema, whichever path is chosen.

## Flutter live rich text editing — what Flutter 3.44.8 / Dart 3.12.2 can actually do inside an editable field

**BLUF.** The repo pins Flutter 3.44.8 stable / Dart 3.12.2 (pubspec `sdk: ^3.12.2`, `flutter: '>=3.41.0'`). The one and only supported extension point for live styled text inside an editable field is overriding `TextEditingController.buildTextSpan`, and it carries a hard invariant that is almost entirely undocumented: the returned span tree's flattened plain text must be position-for-position identical to `TextEditingValue.text`, with every `WidgetSpan` counting as exactly one UTF-16 code unit (U+FFFC). The framework never asserts this — I proved first-hand that violating it produces no error, just silently wrong caret/selection/delete behaviour. Inline widgets do render, lay out and receive taps inside an editable field, but the editable's height ignores them unless you turn off `forceStrutHeight`, `TextSpan.recognizer` trips a framework assertion in any non-readOnly field off macOS, and there is no float/exclusion API anywhere in Flutter's text stack, so text cannot wrap around a multi-line image. Everything below is derived from the pinned SDK source at /opt/homebrew/share/flutter, from probes I wrote and ran against this repo, and from upstream issues I opened individually; I did not read any embargoed path.

### Options this area leaves open

- Single editable field + length-preserving buildTextSpan: one TextField over the whole note, styles derived purely from the stored text (markdown source stays in the buffer), markers collapsed with fontSize:0 when hidden. Keeps all free machinery (undo, IME, selection, shortcuts) and the invariant is trivially satisfiable because nothing is added or removed. Proven working in-probe.
- Single editable field + one-BMP-char image sentinel: images stored as a single U+E000-range private-use character in the text, mapped 1:1 to a WidgetSpan in buildTextSpan, with `strutStyle: StrutStyle.disabled` so the line grows, and tap/select/resize handled by a GestureDetector inside the WidgetSpan (never TextSpan.recognizer). Every leg of this is individually verified; the invariant is preserved by construction because one stored char equals one U+FFFC.
- Block/segment architecture: the note is a list of blocks, each text block is its own small TextField, each image block is a plain widget outside any editable field. Sidesteps the WidgetSpan-in-editable bug cluster and the whole-paragraph relayout cost entirely, at the price of hand-building cross-block selection, cross-block backspace-merge, and cross-block caret navigation — none of which the framework provides.
- Edit/preview split (editable plain source, styled read-only render): a readOnly RichText/Text.rich view can use TextSpan.recognizer freely (verified: no assertion, taps fire) and RenderParagraph DOES grow for tall WidgetSpans (verified 300x60 vs the editable's 300x14). Costs the 'live' feel; buys back a much larger rendering capability surface.
- Writing a custom TextInputClient with `enableDeltaModel: true` to get true per-keystroke deltas. Technically available in dart:ui/services, but it means reimplementing EditableText — selection, handles, toolbar, shortcuts, magnifier, undo, scroll, a11y all become yours.
- For the scrapbook wrap requirement specifically, since no float layout exists: approximate a float with per-line geometry, e.g. an image positioned in a Stack over the text with per-line leading/trailing zero-width-space or spacer padding computed from the image rect, or an image pinned to the start/end of a line with the surrounding text laid out around it in separate paragraphs. All of these are hand-built layout, not text-engine features.

### Ruled out, with reason

- **True CSS-style float: an image on the right of a paragraph with body text wrapping around it across multiple lines, using Flutter's text engine** — dart:ui exposes no exclusion path, float, or shape-fill API. `ParagraphBuilder.addPlaceholder` reserves an inline box on ONE line ('Lines are permitted to break around each placeholder') and PlaceholderAlignment offers only vertical alignment modes. The request to expose lower-level layout for exactly this class of problem (flutter/flutter#35994, which explicitly lists 'Filling a non-rectangular shape with text') was CLOSED 2020-01-06 and locked. Any wrap effect must be hand-built geometry above the text engine, in both editable and read-only text.
- **Using `TextSpan.recognizer` to make inline objects or links tappable inside the editable note** — `RenderEditable.describeSemanticsConfiguration` runs `assert(readOnly && !obscureText)` whenever any span in the tree carries a recognizer and the platform is not macOS (editable.dart:1337-1339). Reproduced on 3.44.8: 23 cascading exceptions including render-tree corruption on TargetPlatform.android; clean on macOS and clean with readOnly:true. Live upstream bug, OPEN P2: flutter/flutter#187598. Use a GestureDetector inside a WidgetSpan instead — verified to work in a fully editable field.
- **A display model whose length differs from the edit buffer — e.g. deleting the `**` markers from the rendered text, collapsing an image filename to one glyph, or rendering a multi-char token as a single chip** — RenderEditable computes every caret, selection and deletion offset from `_textPainter.plainText`, where a WidgetSpan is exactly one U+FFFC code unit. Any length mismatch desynchronises every offset after it, and the framework fires NO assertion — I measured valueLen=7 / plainLen=5 with `takeException()==null`. flutter/flutter#150864 shows the user-visible result: backspace deletes a character two positions away. Maintainer confirmation: flutter/flutter#107432#issuecomment-1186003674.
- **Receiving per-keystroke edit deltas from a Material/Cupertino TextField in order to maintain an out-of-band attributed-range model** — `EditableTextState` mixes in `TextInputClient`, not `DeltaTextInputClient`, and never sets `TextInputConfiguration.enableDeltaModel` (defaults false). You get whole-value snapshots only. Getting deltas requires implementing your own TextInputClient, which forfeits every piece of free EditableText machinery.
- **A block-level widget (full-width image, divider, code block card) as the ROOT of the built span tree** — `TextEditingController.buildTextSpan` is declared to return `TextSpan`, not `InlineSpan` (editable_text.dart:299). The proposal to widen it, flutter/flutter#152066, was closed not_planned in August 2024. Block-level content must be a WidgetSpan child of a TextSpan root, which means it still occupies exactly one code unit and still participates in inline line-breaking.
- **Combining Flutter's built-in spell check with custom live formatting in the same field** — `EditableTextState.buildTextSpan()` returns `buildTextSpanWithSpellCheckSuggestions(...)` and never reaches `widget.controller.buildTextSpan` once `_spellCheckResultsReceived` is true (editable_text.dart:5975-5996). It is either/or. The same short-circuit applies while stylus handwriting (Scribe/Scribble) is active, which is enabled by default.
- **An inline image wider than the field that the user pans horizontally inside the note** — `RenderEditable.performLayout` calls `layoutInlineChildren(constraints.maxWidth, ...)`, clamping every inline child to the editable's width — a declared 400px child measured 150.0 inside a 150px field. Flutter maintainers call this out as wrong in flutter/flutter#90355 ('Should scroll content instead of forcing [WidgetSpan] to size to width') and it is still OPEN and unassigned at P3.

### Open questions

- The `fontSize: 0` marker-hiding technique leaves two caret positions ~0.3px apart. What does arrow-key and selection-drag UX actually feel like across a hidden marker on a real device, and does Android's Gboard cursor-drag / spacebar-swipe cope? My evidence is geometric (caret rects), not interactive.
- Does the U+E000 BMP private-use sentinel survive round-tripping through the Android IME? ### Surprises

- Flutter's supported extension point for live rich text carries a strict positional invariant that appears in NO widgets-layer documentation. The only places it is written down are a dart:ui doc comment about `addPlaceholder` and a 2022 GitHub comment — and Flutter's own triage still links that GitHub comment as the canonical explanation four years later.
- There is NO assertion enforcing that invariant, not even in debug mode. I broke it by two code units and the framework rendered happily with silently wrong caret math and `takeException()==null`. Every other structural contract of comparable importance in Flutter asserts loudly.
- `RenderParagraph` and `RenderEditable` size DIFFERENTLY for byte-identical span trees: 300x60 vs 300x14 for a 60px inline image. The read-only path just works; the editable path clips. The cause is a default (`forceStrutHeight: true`) that exists for a completely unrelated reason — protecting against font-fallback height jitter — and the fix is a documented one-liner that nobody connects to the image problem.
- Flutter's own text-input team filed the oversized-WidgetSpan gap themselves in 2021 (#90355), described it accurately, labelled it P3, and it has sat open and unassigned for five years with the last comment in 2022.
- Putting a `recognizer` on a TextSpan in an editable field does not merely misbehave — it trips a framework assertion and then corrupts the render tree with 23 cascading exceptions. And the assertion is platform-gated to skip macOS, so this is a bug you will never see while developing on a Mac desktop target and will hit immediately on Android.
- Inline widget children DO receive taps inside a fully editable TextField and win the arena against caret placement. Given how much of the surrounding surface is broken, this working cleanly is the opposite of what the issue tracker would lead you to expect.
- Fourteen months of releases (3.32 → 3.44, ~41 commits across the six relevant files) contain zero movement on rich-text editing. `git log -S hitTestInlineChildren` over that range returns nothing at all. The area is not merely unfinished, it is static — planning should assume no upstream help arrives.
- The proper API for this was actually written: PR flutter/flutter#80185 added WidgetSpan support plus a `ReplacementTextEditingController` / 'Replacements' API in April 2021, and was closed unmerged two months later. The workaround everyone uses today is a maintainer's informal sketch of what that PR would have done properly.

## Text wrapping around a shape — Flutter capability, techniques, reference implementations, and measured performance

**BLUF.** Flutter has no text-exclusion / flow-around API at any layer — not dart:ui, not TextPainter, not RenderParagraph, not the skparagraph engine underneath. Every layer accepts exactly one scalar width per paragraph, and I verified this by reading the source on disk and upstream. Flow-around text is therefore always synthesized above the engine by slicing the text into vertical bands of constant width and laying out one paragraph per band; two independent packages ship this today and I measured the cost as negligible (16 slices cost ~11% more to lay out than 1). The load-bearing constraint is not performance and not wrapping — it is that every working implementation is render-only. Flutter's editable text path (RenderEditable) funnels through a single TextPainter with a single width, so "live editor" and "text wraps around the image" are, as of today, two requirements that no Flutter code in existence satisfies simultaneously.

### Options this area leaves open

- BAND SLICING IN PURE FLUTTER (the mainstream option). Maintain float rectangles; for each vertical band compute the free [left,right] span; lay out one ui.Paragraph per band at that width; find each split offset with getPositionForOffset at the band boundary. Proven twice in production (float_column, hyper_render). Measured cost: +11% layout for 16 slices vs 1; a full-rebuild drag frame is <1% of a 60Hz frame at 711 words. Breaks: N RenderParagraphs means selection needs a custom SelectionContainer delegate, semantics fragment per slice, justified text needs the hidden-trailing-word hack. Fatal for editing as-is: no EditableText integration exists.
- ADOPT float_column DIRECTLY for the rendered/preview view. Mature (4.1.3, 7.2k downloads/30d, Flutter-only dependency, MIT), ships selection, RTL, clear, drop caps, margins, nested float columns, maxWidthPercentage. Costs: CSS-float placement model only (no x/y), render-only, and you inherit its justification machinery.
- GENERALIZE SLICING TO ARBITRARY SHAPES. float_column's findSpaceFor already steps bands over a List<Rect> at 1.0px granularity; feeding it per-line rects derived from intersecting a shape (circle/polygon/alpha mask) with each line's vertical band gives true shape-outside. Nobody has built this in Flutter. Measured slicing cost says even one slice per line is affordable. Cost: you own the geometry and the split-convergence loop.
- RESTRICT PLACEMENT SO WRAPPING IS TRIVIAL (the avoid-the-problem option). Allow images only at a small set of anchors — full-width block, float-left, float-right, pinned to a paragraph boundary. Wrapping collapses to two slices: N narrow leading lines, then full width. This is also what makes the owner's responsive compaction fall out for free: below a minimum line width, promote the float to a full-width block and text lands above and below it. Cheapest, sturdiest, and directly satisfies the worked example. Cost: not literally "anywhere".
- SPLIT THE MODES: edit in plain/source view (a normal TextField, no wrapping), render wrapped in a preview/read view. Sidesteps the one genuinely unsolved problem entirely and lets you use a shipping package for the hard half. Cost: "live editor" becomes live-preview rather than WYSIWYG-with-wrap.
- WEBVIEW + contenteditable. Buys float, shape-outside, editing, selection, IME and accessibility from the browser in one move, and macOS is genuinely supported (wkwebview 3.26.1 manifest declares it). Costs: duplicate the design system in CSS, platform-view compositing, a long tail of open Flutter keyboard/focus/IME issues against webview_flutter, local-image asset plumbing, an XSS surface over user content, and a third native story when iOS lands.
- NATIVE PLATFORM VIEW PER PLATFORM. On Apple, NSTextContainer.exclusionPaths gives true arbitrary-path exclusion; on Android, StaticLayout.Builder.setIndents(int[],int[]) gives per-line indents honored by LineBreaker. Both targets can do real shape wrap natively today. Costs: two (then three) native text implementations, no Flutter theming/selection/semantics integration, platform-view overhead.
- OWN THE LAYOUT: a custom RenderObject with LineConstraints/LineSegment semantics, as super_editor's maintainer described. The only path that makes wrapping AND editing work natively in Flutter. Highest cost by a wide margin; you reimplement caret, selection, IME mapping and semantics across slices.
- KEEP PARAGRAPHS WHOLE AND ONLY RE-LAYOUT DURING DRAG. Because re-layout is 11.5x cheaper than rebuild, a design that keeps slice boundaries stable while an image is being dragged and only varies band widths will be close to free; re-split on drag end. A performance lever worth having even if it does not decide the architecture.

### Ruled out, with reason

- **Set an exclusion path / shape on Flutter's paragraph at any layer (dart:ui, TextPainter, RenderParagraph, or the engine)** — The API does not exist and there is nothing underneath it to expose. ParagraphConstraints has exactly one field, `width` (text.dart:2697). ParagraphStyle's full runtime toString lists 12 options, none an indent or exclusion. TextPainter.layout takes scalar minWidth/maxWidth (text_painter.dart:1221). Upstream skparagraph's own entry point is `virtual void layout(SkScalar width) = 0;`. A grep for exclusion/shape-outside/obstacle across all of lib/ui and txt returns only BlendMode.exclusion.
- **Use a WidgetSpan / ParagraphBuilder.addPlaceholder so text flows around the image** — Measured, not inferred: a 140x140 leading placeholder at width 380 produces line 0 with height 145.0 and line 1 starting at y=145.2. Exactly one line of text sits beside the image; all remaining lines start below its full height. Total paragraph height went 192 -> 313 for identical text. Placeholders are inline-block boxes that inflate one line, not floats. They remain the correct tool for a full-width inline image.
- **Escape the paragraph engine by drawing text through a Canvas, CustomPainter, or an SVG text layer** — Canvas text drawing consumes a ui.Paragraph (or a TextPainter that wraps one), so it inherits the identical single-width constraint — dart:ui exposes no way to submit pre-positioned glyphs, and Paragraph has no getPath (grep count 0 in text.dart, though skparagraph's C++ Paragraph::getPath exists unexposed). flutter_svg renders SVG text through the same engine. This buys nothing unless you implement your own shaping, which is the custom-RenderObject option under a different name.
- **Use CSS shape-outside / float inside Flutter itself** — Flutter has no CSS engine. The only route to CSS is a WebView platform view, which is a separate option with a separate cost profile. Note also that the closest pure-Flutter HTML renderer, flutter_html 3.0.0, has zero float support (grep for 'float' in its style.dart returns nothing); only hyper_render implements float, in its own layout engine rather than via CSS cascade.
- **Reach flow-around via Flutter Web's HTML renderer** — It was removed from the framework (SDK commit 4e6e24f7295 '[web] Cleanup everything HTML from the framework'), and web is not a target here — the app ships macOS and Android, with iOS later.
- **Use an existing Flutter rich-text editor (super_editor, flutter_quill, AppFlowy, Fleather) and turn wrapping on** — None implements it and super_editor's maintainers explicitly scoped it out: issue #2439's inline image/widget work states it does NOT include 'document-level line flowing, e.g., paragraphs flowing around images'. All of these editors render text through RenderParagraph/EditableText, which is the single-width path. There is no flag to turn on.

### Open questions

- THE DECIDING QUESTION: does text need to wrap around the image WHILE TYPING, or only in a rendered/preview view? Wrap-in-preview is a solved problem with two shipping packages and measured-negligible cost. Wrap-while-editing has no existing implementation anywhere in the Flutter ecosystem and requires either a WebView, a native platform view, or a custom RenderObject with line-level constraints. These are different projects, and nothing else in this survey matters as much as this answer.
- What does "place an image ANYWHERE" actually mean to the owner — arbitrary (x, y) on the note, or CSS-float-style anchors (left/right at a point in the text)? float_column has no positional field at all. Arbitrary (x,y) additionally forces a decision about what happens when the note reflows and the anchor point moves, which the worked example does not cover.
- Device-measured performance on a mid-tier Android phone. All my numbers are flutter_tester on Apple Silicon. The headroom is large (0.147 ms for a 12-slice drag frame), but the multiplier on a real Android device is unmeasured and the design should not bank a specific number.
- Does float_column's selection hold up at note scale on the target devices? hyper_render markets 'crash-free text selection at any document size' as a differentiator, which implies a known failure mode in the incumbent. This should be probed directly before adopting.
- Accessibility: N sliced paragraphs produce N semantics nodes. What do TalkBack and VoiceOver actually read for a note whose body is split into 6 slices around an image? float_column's own source shows it already fights the framework here (inert spans with empty semantics labels for the justification hack).
- Markdown round-trip: standard Markdown cannot express float side, width, or position. What is the persisted source format, and does it stay diffable/portable? This constrains the editor as much as the layout does.
- If iOS arrives later and the chosen path is a native platform view, the Apple side needs TextKit 1 vs TextKit 2 settled — exclusionPaths is supported in TextKit 2 but has open Apple forum reports of crashes with nil viewportRange and of enumerateTextLayoutFragments misbehaving with .ensuresLayout.
- Whether the webview_flutter macOS path is actually production-usable for a focused, IME-driven editing surface, given the manifest says supported but a 2026-09-03 Flutter issue asserts the opposite and there is a long history of keyboard/focus bugs against the plugin.

### Surprises

- Android already ships the exact primitive Flutter lacks — StaticLayout.Builder.setIndents(int[] leftIndents, int[] rightIndents), a per-line indent array threaded straight into LineBreaker — and Flutter on Android never uses it, because Flutter brings its own skparagraph instead of the platform text stack. The capability is on the device; Flutter just cannot reach it.
- Slicing costs almost nothing. I expected N paragraphs to cost roughly N times one paragraph. Measured: 16 slices of the same 3798-char text lay out in 0.059 ms vs 0.053 ms for one — +11%. Shaping (build) is what scales with slice count, layout barely does. An initial noisier benchmark even showed slicing as FASTER; I re-ran with build and layout separated, which is how I know the +11% figure is the real one and the earlier result was noise.
- Re-layout is 11.5x cheaper than rebuild (0.025 ms vs 0.285 ms). This inverts the intuition about drag performance: the expensive thing is re-splitting the text, not re-flowing it, so a drag that holds split points stable is nearly free.
- An inline WidgetSpan does not wrap text around an image at all — it makes one 145px-tall line. Almost every informal discussion of this problem proposes WidgetSpan first, and it is measurably wrong.
- float_column is genuinely mature (7.2k downloads/30d, 160/160 pub points, Flutter as its only dependency, published 19 days ago) and yet contains not one reference to EditableText, TextField, or TextEditingController. The ecosystem's best answer to this problem is a renderer, and that is not an oversight — super_editor scoped the same feature out explicitly.
- The cost of slicing is not in layout, it is in everything downstream: float_column needs a hand-written MultiSelectableSelectionContainerDelegate, and to justify text it renders a hidden extra word on a clipped line below each chunk and then teaches the selection delegate to skip it. 'Robust does not mean complex' will be tested hardest here, not in the wrapping math.
- macOS WebView support is contradicted by Flutter's own issue tracker. The plugin manifest for webview_flutter_wkwebview 3.26.1 declares a macos platform; a Flutter issue opened 2026-09-03 states the package 'lacks native desktop support for Windows and macOS'. The manifest wins, but anyone reading the tracker would conclude otherwise.
- Flutter's issue #35994, the one result that search engines surface as evidence that 'Flutter supports exclusion paths', is closed and its exclusion-path mention is a link to APPLE's documentation inside a feature request. I checked because an automated summary asserted the opposite; prior conclusions in this area are contaminated by that misreading.

### Options this area leaves open

- Content-driven float demotion: compute the float decision from the measured text-column width divided by (0.48 x fontSize x effective textScaler), i.e. 'float is allowed only while the gutter beside it holds at least N characters'. This falls out of the measurements and automatically handles narrow windows, split-screen panes, rail-constrained desktop panes, and accessibility font scale with one rule instead of three.
- Window-size-class breakpoints (Material 3: 600/840/1200) applied at the shell, with a separate, local LayoutBuilder rule inside the note body. Simplest to explain and matches Flutter's documented idiom; needs a second rule anyway for text scale.
- Store placement as (anchor in document order, side, width fraction) and nothing else — the exact shape float_column already consumes. Anchor survives reflow by construction; side collapses to 'none' under compaction; fraction shrinks with the column. This is a small additive schema change to EntryPhotos.
- Split the surfaces: read/preview renders with float_column and gets true wrap-around on wide screens; the editing surface is a plain EditableText where images are block-level WidgetSpans. Cheap, sturdy, and the only option that gets real wrap at all — at the cost of the editor not being WYSIWYG for the float.
- Block-document model (paragraph list) where each text block is independently editable, so a floated image can be attached to a specific paragraph block and that block alone renders as a FloatColumn when unfocused. Gets closer to WYSIWYG without reimplementing text layout.
- Never float: images are always block-level, full-width or centered, text always above and below, on every screen size. This is the sturdiest and cheapest option and it makes the phone case trivially correct — but it discards the owner's desktop half of the worked example, so it is a product decision, not an engineering one.
- Wire the dead textScaleProvider into a MediaQuery override at the MaterialApp builder so the in-app text-size setting composes with the OS scale, and read the combined scaler in the float-demotion rule.
- Set a macOS contentMinSize so the window cannot be dragged below the width at which the shell is designed to work, reducing the number of layouts that must be correct.
- Capture and persist photo width/height at pick time so the float's box can be reserved before decode, removing the reflow jump.

### Ruled out, with reason

- **Store an image position as absolute pixel x/y on the note canvas** — Two independent failures. First, at half width an absolute x lands outside the column with nothing sensible to do about it. Second and fatal: nothing in Flutter re-flows paragraph text around an arbitrary rectangle — core text layout takes one maxWidth per paragraph, and float_column's model is an anchored child in document order, not a free rect. An absolute position has no renderer that can honor it.
- **Get CSS-style wrap-around inside a live EditableText using core Flutter (WidgetSpan / TextPainter placeholders)** — Measured: a 120x120 placeholder in a 360pt paragraph produced a 122pt-tall line while every other line was 22pt, and exactly one line shared that band. Placeholders reserve a full line band; text never flows beside them on subsequent lines. Re-run scratchpad/probes/placeholder_band_probe_test.dart.
- **Get wrap-around inside a live EditableText using float_column** — float_column's source contains zero references to EditableText, RenderEditable or TextEditingController. It splits read-only paragraphs into multiple RichText parts; an EditableText is a single RenderEditable with one paragraph. There is no seam to hook.
- **Place a FloatColumn inside IntrinsicHeight, IntrinsicWidth, or any parent that queries intrinsic dimensions** — RenderFloatColumn throws a descriptive error in debug mode when asked for intrinsics (documented in the 4.1.0 changelog) because computing them would require laying out all the text and floats. It must sit in a bounded-width, unbounded-height context.
- **Keep branching layout on TargetPlatform to satisfy 'renders well at every screen size'** — Measured failure: the macOS branch hard-codes a 216pt sidebar plus a 266pt rail, leaving 216pt of content at a 700pt window and -4pt at 480pt, and the window has no minimum size. Platform also says nothing about an Android tablet in split-screen at 320dp or a foldable at 840dp.
- **Lock Android to portrait, or declare the activity non-resizable, to avoid handling rotation and multi-window** — Android 16 (API 36) ignores screenOrientation, resizeableActivity and aspect-ratio restrictions on any display with smallest width >= 600dp, and the temporary opt-out property is removed entirely at API 37. Tablets and foldables will resize and rotate the app regardless of what the manifest says.
- **Store position as grid cells** — A grid position is only meaningful relative to a fixed column count. The owner's compaction target is a single-column phone layout, where every multi-column grid coordinate collapses to the same cell and the stored information is lost. It also cannot express 'beside this paragraph', which is the only thing the text renderer can act on.

### Open questions

- Must wrap-around be visible while typing, or is it acceptable that the editing surface shows block images and the read/preview surface shows the float? This is the single biggest fork in the design and it determines whether float_column is sufficient or whether a block-document editor is required.
- Should the float decision be made from the window width, the note pane's width, or the measured character gutter? The measurements argue for the gutter, but that is a novel rule for this codebase and needs an explicit product sign-off on the minimum readable measure (N characters).
- Which platform-read mechanism becomes the convention when size-based layout replaces the platform branches — and do the existing TargetPlatform branches (shell sidebar vs bottom bar, Today rail) get converted at the same time or left alone?
- Does the product want float-beside on Android tablets and foldables in landscape (840dp+), or is the float a desktop-only affordance? The compaction rule is the same either way, but the answer changes how much of the Android matrix must be exercised.
- What minimum macOS window size will the product commit to? Nothing sets contentMinSize today, so either a minimum is declared or every layout must be correct down to a few hundred points.
- Should the dead in-app text-size setting (0.9/1.0/1.15) be wired up and composed with the OS text scaler, or removed? Either way the float-demotion rule needs to read the effective scaler, so the answer cannot be deferred past the design phase.
- Is one float per paragraph anchor sufficient, or does 'anywhere on the note' mean multiple floats and left/right alternation? float_column supports both sides and clear, but the storage shape and the editing gesture differ.
- Should photo intrinsic width/height be captured at pick time (a small change to the picker and capture service) so the float box can be reserved before decode, or is a one-frame reflow acceptable?
- On rotate, what must survive beyond widget state — caret position, selection, scroll offset, unsaved draft? Nothing uses RestorationMixin today, so background process death loses everything regardless of rotation handling.

### Surprises

- The app has no responsive layout at all. Both 'adaptive' branches are platform checks, and the two of them read the platform by different mechanisms (Theme.of(context).platform vs defaultTargetPlatform) with different test-injection strategies.
- The user-facing Settings text-size control is wired end to end — UI, controller, repository, provider, tests — into a provider that no widget in lib/ consumes. Changing it has no visible effect.
- The composer completely ignores the software keyboard. At a 360x780 phone with a 336pt keyboard, 202pt of the panel including the bottom of the writing surface sits behind it, and the panel does not move or shrink.
- The phone composer's editable text column is only 248pt wide because of 54pt page padding on each side — 25.9 characters per line at default scale, 11.8 at 200% text scale. There is no room for a float on a phone even before any design decision is made.
- Photo blobs are persisted with NULL width and height because the picker never supplies them, even though the schema and the store API both accept them. The app currently has no way to know a photo's aspect ratio without decoding the file.
- float_column's own changelog says wrapped text ignored the ambient MediaQuery text scaler until July 2026, and that hidden justification words could leak into text selection until August 2026. The package is solid but the sharp edges are recent and it has one maintainer.
- FloatColumn deliberately throws when asked for intrinsic dimensions rather than silently collapsing — a good failure mode, but one that quietly rules out a set of parent widgets.
- Android will strip orientation and resizability restrictions from the app on any display 600dp or wider starting at API 36, with the opt-out removed at API 37. 'Support only portrait on phones' is no longer a strategy anyone can choose.

## Flutter rich-text / markdown editor package landscape, re-derived from scratch as of 2026-09-20

**BLUF.** The landscape splits cleanly in two, and nothing spans the gap. Four real editors exist (super_editor, flutter_quill, fleather, appflowy_editor); all four lay a document out as a single column of one-block-per-paragraph render objects, none can flow text around an embedded object, and none has a single tracked issue on the subject. Exactly one maintained package produces CSS-float text wrap in Flutter — float_column 4.1.3 — and it is a read-only renderer with no caret, because it achieves the wrap by splitting a paragraph's TextSpan into N separate RenderParagraphs at each width change. The underlying reason is a hard framework fact: `ParagraphConstraints` carries a single `width` and dart:ui exposes no exclusion/float/shape API at all, so float is impossible inside one `ui.Paragraph` by construction. Two facts reshape the decision: appflowy_editor is flatly unresolvable against this app (it pins file_picker ^10.2.0 against the app's ^11.0.2), and Flutter's own `EditableText` already supports inline `WidgetSpan` children, so an inline-image editor needs no package at all.

### Options this area leaves open

- Split the problem: buy an editor for editing (super_editor, fleather or flutter_quill) and float_column for a separate read/preview surface. Wrap exists when reading, not while typing. Costs +29 packages with super_editor, +10 with fleather.
- Plain-text markdown editing in a stock TextField (or a lightly-decorated one) plus a float-capable renderer for the read view — float_column for composed widgets, hyper_render if you want HTML/markdown rendered whole. Simplest and sturdiest; no custom text layout anywhere; +1 or +10 packages.
- Build on Flutter primitives with no editor package: a custom TextEditingController emitting WidgetSpans into a real TextField. Framework-supported today (editable_text.dart:6045), gives IME, caret, handles and magnifier for free, and yields inline images at arbitrary text positions — but inline placement, not wrap.
- Adopt fleather for minimum weight (+9, 160/160, MIT) and persist its native Delta JSON, treating markdown strictly as a lossy export. Requires accepting that the shipped markdown encoder drops images entirely, or replacing that codec.
- Adopt flutter_quill for maximum maintenance velocity and an exact SDK match (flutter >=3.44.0), persist Delta JSON, and use `EmbedBuilder.expanded == false` for inline images — accepting that its markdown converter is untested and its image-embed package is 19 months stale.
- Adopt super_editor from a pinned git ref rather than pub, accepting a prerelease, and extend its markdown syntax the way it already extends it for `=WxH` to carry float side and width percentage.
- Fork or extend float_column into an editable widget — the only path to true WYSIWYG float editing, and by far the most expensive, since caret mapping and IME would have to span chunk boundaries that move as the user types.
- Two-mode UX: an edit mode with images as full-width blocks (which every editor supports natively) and a read mode with float. This makes the phone layout free — 'text above and below' is what a block image already does — and confines float to a render-only surface.

### Ruled out, with reason

- **appflowy_editor (any version >= 6.1.0)** — Pins file_picker ^10.2.0; field_notes depends on file_picker ^11.0.2. Pub's solver forbids it outright and offers only appflowy_editor ^0.1.12 or a file_picker downgrade across the whole app. No release since 2025-12-08, and pub's own analysis reports has:error with zero platform tags.
- **Text flowing around an embedded image inside any existing Flutter editor package** — super_editor, flutter_quill, fleather and appflowy_editor all lay out a document as a single column of one render object per block. Text cannot cross or wrap beside a sibling block, and a gh issue search for float+image+text returns zero results in all of them.
- **Achieving float inside a single ui.Paragraph / TextPainter** — ParagraphConstraints carries exactly one `width` field (sky_engine/lib/ui/text.dart:2697-2720) and dart:ui exposes no exclusion, shape-inside or obstacle API. Varying line widths within one paragraph is not expressible. Any float implementation must slice the paragraph into several paragraphs, which is exactly what float_column does.
- **WidgetSpan / addPlaceholder as a float mechanism** — A placeholder is one U+FFFC character occupying an inline box. Lines break around it; following lines do not wrap beside it (text.dart:3518, 3532-3534).
- **Editing text that wraps around a float using float_column as shipped** — float_column is render-only: no EditableText, TextField, TextEditingController, caret or cursor anywhere in its source. It also asserts on computeDryLayout. Selection works; editing does not exist.
- **Standard markdown as a lossless single source of truth for scrapbook geometry** — CommonMark has no syntax for image side, width percentage or position. Every project needing it invents a non-portable extension — super_editor's `![alt](url =500x200)` and `:---:` alignment notation are the existing proof.
- **flutter_markdown as the render layer** — Discontinued and unlisted on pub.dev. The maintained path is flutter_markdown_plus 1.0.12.
- **livemd_flutter** — Its declared repository URL returns HTTP 404, so the source cannot be reviewed at all.
- **lexical_flutter, flutter_quill_kit, or the Flutter-Bounty-Hunters prosemirror port as a foundation today** — Repos created 2026-07-25, 2026-08-15 and 2026-08-30 respectively; 2, 0 and 1 stars; 0-2 likes each; the prosemirror port carries an unrecognised licence. No production track record exists to evaluate.

### Open questions

- Does wrap have to be live WHILE EDITING, or is wrap-in-read-view acceptable? This one answer collapses the landscape: read-view-only is a solved problem with float_column; live-wrap-while-editing has no package and no framework support.
- Does 'anywhere on the note' mean free/absolute positioning, or anchored-to-a-text-position float? float_column only does the latter (a float anchors to the line of text containing its WidgetSpan). Absolute positioning plus reflow is a different and much harder problem.
- Must the on-disk format be markdown, or is markdown only an interop/export format? The app already has drift; if markdown is not the source of truth, every lossy-codec finding above stops mattering.
- If markdown must be the source of truth, is a non-portable extension acceptable for float side and width (the way super_editor already did for `=WxH`)? CommonMark cannot express this any other way.
- How many images per note, and how large? float_column re-splits and re-lays-out every affected paragraph on each layout pass and cannot compute a dry layout — the performance envelope needs measuring against a realistic note before it is designed around.
- Is a single-maintainer dependency acceptable for a core UX pillar? float_column (ronjb, 147 commits, 5 years) and hyper_render (one contributor, 9 months) are both bus-factor-1.
- Is depending on a prerelease or a git ref acceptable? super_editor has no stable release and its maintainers explicitly recommend depending on the repo.
- Which feature-rich markdown features are actually in scope — tables, code blocks, task lists, footnotes? super_editor and appflowy have tables; parchment's codec ignores nested blocks entirely.

## Product precedent and interaction design for "place an image anywhere in a note and have text wrap around it," desktop + Android

**BLUF.** No shipping note-taking app wraps body text around a placed image. Genuine wrapping survives in exactly two lineages — page-layout word processors (Word, Pages, Google Docs) and web publishing (Wikipedia, Medium, EPUB/KF8) — and neither solves the phone the way the product owner imagines: word processors do not reflow to phone width at all (they render a fixed page you pan and zoom, or switch to a separate reflow mode that drops objects), while web publishing un-floats the image and stacks it, which is precisely the owner's worked example and is the only pattern with a proven track record at every screen size. Every note app examined (Notion, Craft, Bear, Apple Notes, Apple Journal, Day One) quietly avoids the problem by making images blocks; every scrapbook/collage app (Canva, PicCollage, GoodNotes, Freeform, OneNote) buys free placement by abandoning text reflow entirely, putting text in its own absolutely-positioned object. Measured on a real 375px phone column, a floated image at 40% width leaves 26 characters per line against a 45-character readability floor, so on a phone wrapping is not merely awkward, it is typographically impossible — the compaction the owner describes is not a nicety, it is the only correct behavior.

### Load-bearing findings

- **Microsoft Word's model is the full reference implementation: an image is either In Line with Text (behaves as a text character) or floating with one of Square, Tight, Through, Top and Bottom, Behind Text, In Front of Text. Every floating mode is bound to a hidden anchor character in a paragraph, and the anchor has two policies: Move with Text or Fix Position on Page.**
  - evidence: `https://support.microsoft.com/en-us/office/wrap-text-around-a-picture-in-word-bdbbe1fe-c089-4b5c-b85c-43997da64a12 and https://support.microsoft.com/en-us/word/wrap-text-and-move-pictures-in-word`
  - confidence: high
- **Apple Pages uses the same two-axis model with friendlier names: object placement is Move with Text (an anchor marker appears in the text) or Stay on Page, and text wrap is one of exactly five values — Automatic, Around, Above and Below, Inline with Text, None. Pages ships this full model on iPhone, not just Mac.**
  - evidence: `https://support.apple.com/guide/pages-iphone/place-objects-with-text-tand6205cf6d/ios`
  - confidence: high
- **None of the three word processors solves the narrow-screen case by reflowing a wrapped layout. Word Mobile makes it an explicit user choice between two incompatible views: Print Layout, which 'will render all your objects without any loss of context' but which you must pan and zoom, and Mobile View, which reflows text to screen width but 'does not render certain objects like Ink (signatures) and Shapes' and 'can cause loss of context'. Reflow mode is phone-only, not available on tablets.**
  - evidence: `https://support.microsoft.com/en-us/word/mobile-view-and-print-layout-in-word-mobile ; tablet exclusion at https://learn.microsoft.com/en-us/answers/questions/5306079/`
  - confidence: high
- **OneNote — the one Microsoft product that genuinely offers free placement of text containers and images on an infinite canvas — has the same answer on a phone: pan and zoom. Its mobile experience is widely described as requiring panning and zooming to see page contents rather than reflowing into a single column.**
  - evidence: `https://www.xda-developers.com/used-onenote-for-years-but-hidden-settings-changed-note-taking-habits/ and https://www.noteapps.ca/onenote/`
  - confidence: medium
- **Notion does not wrap text around images at all. Images are blocks, resizable by dragging guides on the left and right edges, alignable left/center/right; the documented workaround for text-beside-image is a two-column layout.**
  - evidence: `https://www.notion.com/help/images-files-and-media and https://super.so/blog/wrap-text-in-notion`
  - confidence: high
- **Notion's own documentation states the compaction rule the product owner described, verbatim: 'Columns are available on tablet but not mobile.   - evidence: `https://www.notion.com/help/columns-headings-and-dividers`

### Options this area leaves open

- The Wikipedia/Medium pattern: an image is a flow object with a side preference (left/right/center) and a width fraction, honored as a genuine float above a width threshold and demoted to an un-floated, width-capped, centered block below it. This is the only pattern in the survey with a proven record at every screen size, and it is literally the owner's worked example. It also matches the measured 45-CPL floor and lands its breakpoint near Material's 600dp compact boundary.
- The Notion pattern: no wrapping at all; text-beside-image is expressed as a two-up row that stacks on compact widths. Simpler than floats, no anchor semantics, no partial-line layout, and already proven to degrade correctly — but it cannot express a small image with text flowing around three sides.
- The Word/Pages anchored-object model in full: anchor to a paragraph, choose Move with Text vs Fix Position, choose from a small set of wrap modes. Maximum expressiveness and the model users transfer from word processors, but it brings anchor drift, an invisible anchor character, and no phone story that any vendor has solved by reflow.
- A two-mode product, the way Word Mobile and OneNote split it: a rich placement mode on wide windows and a reading/compact mode that linearizes. Honest about the incompatibility rather than pretending it away, at the cost of teaching users two mental models.
- Free-canvas scrapbook mode as a distinct artifact type alongside — not inside — the flowing note (the Canva/Freeform bargain): absolute coordinates, rotation, tape, layering, and no text reflow, rendered as a fixed-aspect canvas that scales rather than reflows. Preserves the scrapbook aesthetic exactly, and sidesteps every wrapping problem by not having flowing text on that surface.
- A hybrid: flowing Markdown body with floated/blocked photos, plus per-photo decoration (tilt, tape, frame) applied as a purely visual transform inside the photo's reserved box, so the aesthetic survives while the layout box stays axis-aligned and reflowable.
- Placement expressed as intent (side + size + anchor paragraph) rather than coordinates, so the renderer is free to compact. Every product that survives narrow screens stores intent; every product that stores coordinates needs a separate AI re-layout pass (Canva Magic Switch) and still produces a draft.

### Ruled out, with reason

- **Absolute x/y coordinates for photos inside a reflowing note, resolved responsively at render time** — No product in the survey does this, including the ones whose entire business is free placement. Canva stores absolute coordinates on a fixed canvas and its answer to a new size is Magic Switch, which produces a separate copy in a new folder and still yields overflowing text and awkward crops that need manual fixing (https://www.canva.com/pro/magic-resize/). OneNote and Freeform store coordinates and answer the phone with pan-and-zoom. Coordinates and reflow are not reconcilable; the market has tried and settled.
- **Text wrapping around a floated image on a phone** — Measured, not asserted: a 375px phone gives a 343px text column at 47 characters per line before any image, already at the bottom of the 45–75 band. A 40%-wide float leaves 26 CPL; at Android's supported 2.0x font scale the column gives ~23 CPL with no image at all. Wikipedia, which floats aggressively on desktop, sets float:none on its mobile host. This is not a rendering-engine limitation to be engineered around — there is no readable text to wrap.
- **A desktop-style hover-revealed resize handle as the primary placement affordance** — There is no hover on touch, long-press is documented as undiscoverable with no visual indicator (https://www.nngroup.com/articles/contextual-menus/), a long-press-to-drag races the scroll recognizer which claims the touch in under 100ms, and WCAG 2.2 SC 2.5.7 (AA) requires a non-dragging single-pointer alternative for any drag functionality regardless. A drag-only design fails discoverability, gesture arbitration and conformance simultaneously.
- **Inheriting Word's implicit anchor behavior (auto-anchor to the nearest paragraph, image must share a page with its anchor)** — This is the single most-complained-about behavior in the entire corpus — images jumping pages when text above them is edited, users taught a four-step Lock anchor incantation as a workaround. The anchor is generated by the app, invisible by default, and the user never consented to it. Importing it imports its support burden.
- **Relying on a floated image plus a media query as the whole responsive story, with no minimum-measure rule** — The breakpoint has to be derived from the remaining text column, not the viewport. A 260px image in a 700px column is fine (58 CPL); the same image in a 560px column is not. A viewport-only rule breaks the moment a sidebar, split-view, large font scale, or a wider image changes the available measure — and Android 14's 0.85x–2.0x font scale changes it by a factor of 2.4 without the viewport moving at all.
- **Assuming a mature note app already has a wrapping model to copy** — Checked all of them: Notion (blocks + columns), Craft (auto-grouped blocks), Bear (inline attachments), Apple Notes (Small/Large view only), Apple Journal (attachment group at top), Day One (app-managed media). Zero wrap. Obsidian only via a third-party CSS snippet whose own docs admit text selection beside a float-left image is 'still not possible'. There is no note-app prior art to copy; the prior art is in word processors and web publishing.

### Open questions

- Does the product owner's 'anywhere on the note' mean anywhere in the text flow (a float anchored to a paragraph, Wikipedia-style) or anywhere on a 2D surface (absolute coordinates, Canva-style)? The survey shows these are different products with different failure modes and no shipping example reconciles them. This is the single question a design phase cannot start without.
- Is the note a fixed-width page that scales (Pages/Canva) or a fluid column that reflows (Wikipedia/Notion)? Every other decision follows from this and no product in the survey does both.
- What is the authoring surface on a phone — can a user place and float an image from Android, or is placement a wide-window capability with phones getting view-and-reorder only? Notion took the second path explicitly. Worth asking whether the owner considers phone authoring of placement a requirement or a nice-to-have.
- Should the image's side preference be preserved when the float is demoted on a phone (a left-floated image becoming a left-aligned capped block) or normalized to centered as Wikipedia does? This is a small decision with a visible identity consequence for a scrapbook aesthetic.
- Does the scrapbook aesthetic need real rotation of the layout box, or is a purely visual tilt inside a reserved axis-aligned box sufficient? The former makes wrapping intractable; the latter is cheap. Users may not be able to tell the difference, but the owner might care.
- What happens to a placed photo when the note is exported, shared, or rendered to plain Markdown? Every wrapping model here needs out-of-band metadata that standard Markdown cannot carry, so the persistence format constrains the interaction model.
- How many photos does a typical entry actually have today? The current InlinePhotoStrip is a horizontal scroller, which implies the design anticipated many — and the wrapping models in the survey degrade badly past two or three floats in one column of text (Wikimedia's own guidance warns specifically about multiple floated elements).
- Does the owner accept a minimum-measure rule that can override their placement — i.e. the app sometimes refusing to float an image because the remaining column would be unreadable, even on a wide screen with a large image? Every robust implementation needs this, and it means the app occasionally overrules the user.

### Surprises

- Apple Pages ships the complete anchored-object + five-mode text wrap model on iPhone — a phone-sized screen. It gets away with it because Pages does not reflow the document to the screen; it renders a fixed page you pinch and pan. The existence of wrapping on a phone is not evidence that wrapping works at phone width.
- Microsoft, who invented this problem space, does not solve it responsively. Word Mobile makes the user choose between an unreadable-but-faithful Print Layout and a readable Mobile View that silently stops rendering shapes and ink and is documented as causing 'loss of context'. Reflow mode is phone-only and unavailable on tablets — the industry leader shipped a mode switch, not a responsive layout.
- Notion's help page states the owner's worked example almost word for word as a product limitation ('on your phone, you'll see the content in any right-hand column simply placed under the content in the left column') and additionally refuses to let users create columns on a phone at all. The biggest note app in the world treats compact-width layout authoring as out of scope.
- On mobile Wikipedia the un-floated figure is 250px in a 343px column — centered and capped, not stretched to full width. The correct compaction of a float is not 'make it full-bleed'; it is 'stop floating it and keep it modest', which preserves the sense that the image is an inset rather than a chapter break.
- At 375px with 16px body text the full-width column is already only 47 characters per line. The phone is at the readability floor before a single image is placed. This reframes the whole problem: the design budget on a phone is not 'how do we fit an image beside text', it is 'we have no horizontal slack at all'.
- The scrapbook aesthetic and text wrapping pull in opposite directions. Tilt, overlap, layering and tape — the actual substance of the aesthetic per the craft literature — all require an object that is not an axis-aligned rectangle in a flow, while wrapping requires exactly that. Word's Tight/Through modes are the only place in the survey where text follows a non-rectangular contour, and both are desktop-only, opacity-dependent, and absent from every note app.
- Every reflowable-text domain that genuinely wraps (EPUB/KF8) reports the same class of bug: an image and its caption splitting across a page boundary, with the recommended fixes described by practitioners as 'bulletproof and currently recommended, but far from optimal'. Keeping an image and its caption together is a named, unsolved problem even in the one industry that has done this for a decade.

Correct the design input to: long-press threshold in the 120-350ms range per shipped implementations, movement-before-timer means scroll, touch-action:none required.
- `OVERSTATED` Long-press is undiscoverable: 'a hidden user interface element' with 'no visual indicators directly suggesting the availability of a prolonged touch action'; mobile gestures 'are not discoverable and have still not become standard'; the conventional signifier is a visible ellipsis or chevron.
  - correction: NN/g carries the third quote and the signifier point verbatim: 'these gestures are not discoverable and have still not become standard', and 'Common visual signifiers for contextual menus include vertical or horizontal ellipsis and down-pointing arrows', plus 'it is unlikely that people will naturally remember to use it later on in the app' even after an onboarding tip — which is the stronger finding and should be the one quoted. The first two quotes ('a hidden user interface element', 'no visual indicators directly suggesting the availability of a prolonged touch action') are attributed to lestroissports.ca, whose DNS does not resolve (SERVFAIL) — the source is dead and the quotes are unverifiable. Also 'will be found by a minority of users' is a quantitative claim with no measurement behind it. The conclusion (do not make long-press the sole path) is correct and is independently required by SC 2.5.7 in claim 21 — lean on that instead.
- `OVERSTATED` The scrapbook aesthetic implies layering, overlap, tilt, rotation and z-order — 'even small imperfections make it feel more handmade and natural' — all properties a wrapping text flow cannot express.
  - correction: The verbatim quote 'even small imperfections make it feel more handmade and natural' does NOT appear on the cited paperwrld page. What that page does say supports the technique claim: layering is 'placing various elements on top of each other to create depth and dimension' and 'Place these elements at different angles to create dynamic layering.' PicCollage corroborates strongly ('Photos overlap at angles with torn paper edges and tape stickers between them', stickers 'peel on and off with a tap'). The washi-tape and mooboom sources were not checked. The closing inference is a design argument, not evidence — and it is only partly true: CSS shape-outside can express non-rectangular wrap contours, so the genuinely inexpressible properties are ROTATION and OVERLAP, not irregular silhouettes. Tighten the inference to those two or it will be picked apart.

## Completeness critic

**Ready to design: False**

### Why not ready

Not ready to choose an architecture. Ready to run a short, well-aimed spike. Three specific reasons, not general caution. FIRST, a central area is citation-unreliable in a pattern, not a slip. Area 7 (product precedent) -- the evidence base for the entire interaction model -- had a verifier find at least three verbatim quotes that do not appear in their cited sources (`usually at the beginning of the paragraph nearest to the top left corner of the figure` appears in `NONE of the three cited sources`; `even small imperfections make it feel more handmade and natural` does `NOT appear on the cited paperwrld page`; `bulletproof but far from optimal` not found), one dead-domain citation (`lestroissports.ca, whose DNS does not resolve`), a headline measurement that did not reproduce (7.37 px/char vs a re-measured 6.904, and `this is desktop Chrome at an emulated 375px, NOT 'a real phone'`), and its load-bearing threshold rated `a judgement dressed as arithmetic`. The area's DIRECTION survives -- Notion's stacking quote is verbatim-confirmed and is the strongest precedent in the set -- but its numbers must not enter a spec, and the ~528px breakpoint that three areas now cite traces back to it. SECOND, zero device measurements exist for a platform that is a hard requirement. Every performance figure in seven areas is flutter_tester or desktop Chrome on Apple Silicon; the Android multiplier is explicitly unmeasured (`plausibly 7-22% on mid-tier Android`), the U+E000 sentinel's survival through Gboard is untested (`Needs an on-device Android test, which I could not run here`), and HEIC decodability on Android is unverified. Android is where the owner's compaction requirement actually bites, and it is the one place nothing was measured. THIRD, the two questions that collapse the option space are product questions nobody has put to the owner: does wrap have to be live WHILE TYPING (four areas independently named this the deciding question), and does `anywhere` mean an anchor in the text flow or a coordinate on a canvas (area 7: `no shipping example reconciles them. This is the single question a design phase cannot start without`). Designing before those answers means designing all branches. What would flip this to ready, in roughly this order and at modest cost: (a) two sentences from the owner answering live-wrap and anchor-vs-coordinate, plus a ruling on whether existing notes may be reinterpreted as markdown; (b) one decision on which width is canonical for reading a note, given the 520pt day-detail cap -- without it the demotion rule has no stable input; (c) half a day on a real mid-tier Android device measuring three things only: keystroke cost in a long note, a scroll frame over a feed of sliced note bodies, and whether an image sentinel survives Gboard; (d) re-derive area 7's threshold from a source that exists, or drop the number and state the rule qualitatively. None of that is research; it is four answers and one afternoon. Until then the ground truth that IS solid -- dart:ui has no exclusion API (verified at engine, framework and package layers, independently, by two areas and their verifiers), float_column's mechanism, and the repo's actual call sites -- is enough to rule options OUT, and not enough to rule one IN.

### Biggest unknown

Whether WYSIWYG is even definable in this app's shell -- because the surface the user edits on and the surfaces they read on have structurally different widths, and nobody in seven areas noticed. Verified from code: editing happens in a full-window `showGeneralDialog` overlay whose LayoutBuilder sees the entire window (text_composer.dart:135-147, day_detail_edit_note.dart:149, confirmed by area 5's own verifier). Reading happens in EntryCard -> NoteBody in two other containers: the Today feed inside the rail-constrained main pane (measured by area 5's verifier at 716pt of a 1200pt window, less 24pt padding each side), and DayDetailPanel, which hard-clamps itself to `maxWidth = 520` (day_detail_panel.dart:30, :79-80). Now apply the survey's own float-demotion threshold -- area 5 derives `a 40% float needs a ~560pt text column`, area 7 independently derives `~505-530px`. The day-detail read panel is capped at 520pt and therefore can NEVER float on any device, at any window size, forever. So under the favoured rule a photo floats in the Today feed, does not float in day detail, and the editor -- at full window width -- shows a third layout again. The same note, same device, same session, three renderings. This invalidates the entire edit-in-blocks-render-with-float family, which is the leading direction in five of the seven areas, because that family's whole premise is that what you see when you read is the authoritative layout and the editor is merely a lesser approximation of it. Here there is no single authoritative layout to approximate. Nothing in the survey addresses this, and it is not a Flutter limitation that a package or a spike can lift -- it is the product's own shell geometry, and resolving it means changing the shell (one canonical note-reading width), changing the demotion rule (content-relative rather than absolute), or accepting that the owner's worked example is only ever true in one of three places.

### What nobody asked

- THE CORPUS ALREADY ON DISK. `entries.text_content` is `text().nullable()` with no format discriminator (lib/data/database/tables.dart:23) and NoteBody renders it raw (lib/features/entry_cards/cards/note_body.dart). The day a markdown renderer ships, every note ever written is retroactively reinterpreted: a line starting with `- `, a `#`, `*` used as multiplication, `_snake_case_`, an indented paragraph becoming a code block. Worse, it is a one-way door -- once a reinterpreted note is opened in a rich editor and saved, the stored bytes change and there is no versioning, no history table and no undo across sessions. Three areas argue about which format to store; not one asks whether existing entries may be reinterpreted, whether they must be pinned to a `plain` format at rest, or whether a one-time normalization pass is acceptable. This must be answered before the storage decision, not after.

- WHICH SURFACE THE WRAP RENDERS ON. Every area reasoned about `a note`. In this app a note body renders in at least three places with different containers: Today feed (today_entry_feed.dart:68, a Column of EntryCards inside the rail-constrained main pane), day detail (day_detail_panel.dart:141, a `ListView.separated` inside a dialog capped at `maxWidth = 520` at :30/:79-80), and via EntryCard in both (entry_card.dart:136). NoteBody has no maxLines and `overflow: TextOverflow.clip`, so the feed renders whole notes, N at a time, lazily. The wrapping area established float_column `cannot compute a dry layout` and the responsive area KILLED `FloatColumn inside IntrinsicHeight, IntrinsicWidth, or any parent that queries intrinsic dimensions` -- but nobody joined those facts to a lazy list of sliced-paragraph note bodies. Question: does a floated photo render in the scrolling feed, or only in a dedicated single-note view? Every performance number in this survey measured one paragraph or one note; none measured a scroll frame over a feed of them.

- THE SAVE MODEL, AND THE ORPHAN BLOBS THAT FOLLOW FROM IT. `showTextComposer` is `barrierDismissible: true` (text_composer.dart:135) as is the edit route (day_detail_edit_note.dart:43,149), and `grep -rni 'draft|autosave|RestorationMixin' lib/` returns zero hits. One stray tap on the barrier discards the work. Today that costs two lines of text; with a long markdown body and three placed photos it is a product failure, and Android process death loses it regardless. The responsive area mentions `unsaved draft` only as a rotation casualty. Nobody asks the product question: explicit-save-only as today, or autosave/draft? It is not cosmetic -- a draft needs somewhere to live (a row, a dirty entry, a file), it forces the create/edit asymmetry to be resolved, and it creates a blob lifecycle problem nobody has named (next item).

- CONTENT-ADDRESSED BLOBS CANNOT BE DELETED ON REMOVE. Photos are SHA-256-addressed files, which means identical bytes are one file shared by every entry that references them -- sharing is a property of the design, not an edge case. In an editor, `remove this photo`, `undo a paste`, and `abandon a draft` all become delete paths, and none of them can safely unlink the file without refcounting. The storage area noted `softDeletePhoto` has no callers and flagged orphan rows for one specific option, but no area asked whether refcounted or GC'd blob deletion exists, is correct, or is in scope. A scrapbook editor makes add-and-remove the primary gesture; today the codebase has only add.

- SYNC. `lib/features/settings/sync/sync_shell_options.dart` ships a `SyncStorageChoice.syncToServer` option alongside a server-URL, access-token and sync-frequency UI (sync_storage_section.dart, all `enabled: false`, copy reading `Where your entries would sync`). That is a declared product direction sitting in the settings screen. If notes ever sync, the note format stops being a storage decision and becomes a wire format and a merge unit: markdown in one column merges as text, Delta JSON merges as operations, a placement sidecar table merges as rows with independent conflict semantics, and content-addressed blobs need a transport story. Seven areas, zero mentions of sync. This is the kind of question that retroactively kills a format choice after it ships.

- RTL AND THE LOCALIZATION COMMITMENT. The entire proposed model is `side` -- float left or float right. `grep` over lib/ for `Directionality|TextDirection|localizationsDelegates|supportedLocales` returns one incidental hit (sidebar_shell.dart:276) and nothing else; there are no localization delegates and exactly one file uses directional insets. So the app has no RTL story at all, and `float right` has no defined meaning under RTL. Separately, two areas flag TalkBack/VoiceOver reading N sliced paragraphs as open, but nobody asked the prior question: what accessibility level is the app committing to? WCAG 1.4.10 (reflow) and 1.4.4 (resize to 200%) are precisely what a float-demotion rule either satisfies or violates, and the app already ships an unused `textScaleProvider` and reads only two accessibility flags from MediaQuery.

- HOW THE THING WILL BE VERIFIED. The repo has 204 test files and exactly five golden tests, all for design primitives (test/design/goldens/). A hand-built slicing or float layout is defensible only by goldens across a matrix -- widths x text scales x platforms -- and the responsive area's own probe was caught being five `debugPrint` subtractions rather than a render. Nobody asked what verification regime the design must be buildable against. This constrains architecture directly: an option you cannot golden across widths (a custom RenderObject, a WebView, a native platform view) is a different maintenance proposition from one you can, and that should be an input to the choice rather than a discovery after it.

### Contradictions between areas

- LIVE-WRAP: AN OPTION IN ONE AREA, KILLED IN TWO. Area 3 lists it: `for the scrapbook wrap requirement specifically, since no float layout exists: approximate a float with per-line geometry, e.g. an image positioned in a Stack over the text with per-line leading/trailing zero-width-space or spacer padding computed from the image rect`. Area 4 kills the family: `Escape the paragraph engine by drawing text through a Canvas, CustomPainter, or an SVG text layer` is in its KILLED list, and its BLUF states `'live editor' and 'text wraps around the image' are, as of today, two requirements that no Flutter code in existence satisfies simultaneously`. Area 5 kills it by name: `Get CSS-style wrap-around inside a live EditableText using core Flutter (WidgetSpan / TextPainter placeholders)`. So the exact technique a designer under schedule pressure would reach for is simultaneously on the table and off it, and nobody adjudicated. Note the two are not strictly the same claim -- the ZWSP/Stack hack fakes wrap without touching the paragraph engine -- which is precisely why it needs an explicit ruling rather than being left ambiguous.

- FLOAT_COLUMN: SOLE OPTION, AND SUSPECT. Area 6 asserts `Exactly one maintained package produces CSS-float text wrap in Flutter -- float_column 4.1.3`, and its own verifier refutes it: `'the only maintained package' is refuted by the same survey's own CLAIM 27: brewkits/hyper_render ships doc/adr/0003-css-float-support.md ... and four float goldens`. Meanwhile area 4 raises a reliability doubt about the same package: `hyper_render markets 'crash-free text selection at any document size' as a differentiator, which implies a known failure mode in the incumbent. This should be probed directly before adopting.` Yet both areas list `ADOPT float_column DIRECTLY` as a leading option and neither reconciles the doubt with the recommendation. The single dependency the favoured direction rests on is bus-factor-1 (`ronjb, 147 commits`) and has an unprobed suspected selection failure at document scale.

- PERFORMANCE: NOT A CONSTRAINT vs A CAP IS NOT OPTIONAL. Area 4 concludes `a whole drag frame rebuilding every slice costs under 1% of a 60 Hz frame; performance is not the constraint on this feature` -- its verifier could not reproduce that (`0.2482 ms, which is 1.49% of a 16.67 ms frame, not 'under 1%'`) and restates it as `plausibly 7-22% on mid-tier Android`. Area 3's verifier concludes the opposite for the same feature on a different axis: `at ~88k chars a single keystroke costs 109ms of Dart-side work ... a document-length cap or a chunked/paginated editing surface is not optional at scale.` One area says performance does not constrain the design; another says it forces a cap or pagination. Neither measured on an Android device, which is a shipping target, and neither measured the two costs together -- which is exactly what an editor with a placed photo does on every keystroke.

- WHERE THE COMPOSER LIVES -- AND THE CORRECTION NEVER PROPAGATED. Area 5's rationale: the note body `sits inside a rail-constrained pane on desktop`, from which it derives a 216pt content column at a 700pt window and a `~560pt` float threshold. Its own verifier: `The composer is not inside the rail-constrained pane: it is presented by showGeneralDialog ... ComposerShell is a full-window route overlay above the shell, so its LayoutBuilder already sees the whole window ... any design that assumes rail subtraction applies to the composer will be wrong.` The BLUF and the threshold arithmetic were never corrected, so the area's headline numbers are still derived from the refuted premise. This is not a pedantic point: the read surface IS rail-constrained and the edit surface is NOT, which means the same note has two different widths in the same app at the same moment (see biggest unknown).

- TWO AREAS RECOMMEND ACTIONS THAT CANCEL EACH OTHER. Area 2 recommends the drift/drift_dev bump: `Does the team want the drift/drift_dev bump to 2.35.0 regardless of the storage decision? The broken CLI and unusable SchemaVerifier are a latent trap`. Area 6's verifier discovers that this exact bump is what makes an editor candidate unresolvable: `super_editor 0.3.0-dev.52 DOES NOT RESOLVE against this app's pubspec at all ... 'because field_notes depends on both flutter_test from sdk and drift_dev ^2.35.0, version solving failed' ... I isolated the cause: delete drift_dev ^2.35.0 and super_editor resolves at 203.` Neither area noticed the interaction. Separately area 2's migration blast radius was measured as `exactly TWO tests` and its verifier ruled that WRONG (`180 -4`), adding `I did not get a full-suite number ... test/features/, test/app/ and test/widget_test.dart were not measured`, so the true migration cost remains unmeasured while being cited as cheap.

## Owner rulings, 2026-09-20

These were put to the product owner as blocking questions and answered:

| Question | Ruling |
|---|---|
| Must text wrap live WHILE typing? | **No.** Wrap only in the read view. The editor shows a photo as a block. |
| Does "anywhere" mean a text position or a page coordinate? | **A spot in the text.** The photo anchors to a position in the flow and moves with it. |
| What happens to existing notes? | **Delete them.** They are test data, not real. No migration, no format flag, no compatibility burden. |
| How to resolve the three-widths problem? | **One canonical reading width.** The shell changes so a note reads at one width everywhere. |

### What these rulings eliminate

- The hand-built text layout engine (no live wrap needed).
- The coordinate-reflow problem (anchors move with their paragraph).
- **The entire no-migration constraint.** The schema is now free.
- The undefined-WYSIWYG problem (one canonical width).

### What remains unresolved

- **No Android measurement exists.** Every performance figure in this survey is flutter_tester or desktop Chrome on Apple Silicon. Android is a shipping target and this machine has no Android SDK. Treat every perf number as desktop-only until measured on a real device.
- **The float/stack width threshold has no trustworthy source.** The ~520-560pt figure traces to an area whose citations included fabricated quotes. Re-derive it or state the rule qualitatively.
- **float_column is bus-factor-1** with an unprobed suspected selection failure at document scale, and a second candidate (hyper_render) was missed by the area that called it the only option.
- **No draft or autosave exists** and both composer routes are `barrierDismissible: true`. One stray tap discards the work. Fine for two lines of text; a product failure for a long note with placed photos.
- **Content-addressed blobs cannot be safely deleted** without refcounting, and a scrapbook makes remove a primary gesture. The codebase today only has add.
